# 第一章：初识智能体

参考资料：Datawhale `Hello-Agents` 第一章《初识智能体》。

这一章的重点不是背诵所有概念，而是建立一个判断框架：什么是智能体、智能体如何和环境交互、LLM 在其中负责什么，以及什么时候应该使用 Agent 而不是固定 Workflow。

## 一、什么是智能体

智能体（Agent）是能够通过传感器感知环境，并通过执行器采取行动，以完成目标的实体。

可以记成四个关键词：

```text
环境 + 感知 + 行动 + 自主性
```

- `环境`：智能体所处的外部世界，例如道路、网页、数据库或用户对话。
- `传感器`：获取环境信息的方式，例如摄像头、用户输入、API 返回结果。
- `执行器`：影响环境的方式，例如刹车、发送消息、执行代码、调用接口。
- `自主性`：智能体能够根据当前信息和目标，自主决定下一步行动，而不是每一步都由人写死。

判断一个系统是不是智能体，不能只看它是否使用了 AI 或 LLM，而要看它是否形成了“感知—决策—行动”的闭环。

## 二、传统智能体的演进

传统智能体可以按照决策能力从简单到复杂理解：

| 类型 | 核心特点 | 典型问题 |
| --- | --- | --- |
| 简单反射智能体 | 根据当前输入直接执行规则 | 现在应该立刻做什么？ |
| 基于模型的反射智能体 | 保存内部状态或世界模型 | 世界现在是什么状态？ |
| 基于目标的智能体 | 通过规划选择能达成目标的行动 | 做什么才能完成目标？ |
| 基于效用的智能体 | 在多个方案之间权衡收益 | 哪个方案最值得选择？ |
| 学习型智能体 | 根据环境反馈改进策略 | 如何从经验中变得更好？ |

这条演进路线可以理解为：

```text
当前规则 → 记住状态 → 规划目标 → 权衡结果 → 从经验学习
```

不需要死记每种类型的定义，重点是理解“智能体的决策依据越来越丰富”。

## 三、LLM Agent 的新范式

LLM Agent 和传统规则系统的主要区别在于：

| 对比项 | 传统智能体 | LLM Agent |
| --- | --- | --- |
| 核心决策 | 显式规则、搜索算法、状态机 | LLM 的语言理解和推理能力 |
| 知识来源 | 人工编写的规则和模型 | 预训练知识、上下文和外部工具 |
| 指令形式 | 结构化输入 | 自然语言目标 |
| 行动方式 | 预先设计的固定路径 | 根据当前结果动态选择下一步 |
| 优势 | 稳定、可控、容易验证 | 灵活、通用、适合处理模糊任务 |
| 风险 | 遇到未覆盖情况容易失效 | 可能幻觉、格式错误或调用错误工具 |

LLM 在 Agent 中更像一个“大脑”，但它本身不是完整的 Agent。只有当 LLM 能够读取环境信息、选择工具、执行行动并根据结果继续决策时，才形成完整的智能体系统。

## 四、Agent Loop：智能体如何运行

智能体不是只调用一次模型，而是通过循环不断和环境交互：

```text
感知 Observation
      ↓
思考 Thought
      ↓
选择并执行 Action
      ↓
环境返回新的 Observation
      ↓
继续循环，直到完成任务
```

对于 LLM Agent，`Thought` 阶段通常包含两件事：

1. **规划**：把复杂目标拆成更小的子任务。
2. **工具选择**：决定下一步调用哪个工具以及传入什么参数。

这个循环是本章最重要的内容，也是前面“旅行助手 Agent”代码的理论基础：

| 理论概念 | `first_agent` 中的实现 |
| --- | --- |
| 感知 / Observation | `tools.py` 返回的天气和搜索结果 |
| 思考 / Thought | LLM 根据系统提示词生成的思考内容 |
| 行动 / Action | `get_weather(...)`、`get_attraction(...)`、`Finish[...]` |
| 记忆 / 上下文 | `agent.py` 中的 `prompt_history` |
| 循环控制 | `run_agent()` 的 `max_steps` |
| 执行器 / 工具 | `available_tools` 中注册的 Python 函数 |

## 五、PEAS：如何描述一个任务环境

PEAS 用四个维度描述智能体所处的任务环境：

```text
P = Performance，性能度量
E = Environment，环境
A = Actuators，执行器
S = Sensors，传感器
```

以旅行助手为例：

| 维度 | 内容 |
| --- | --- |
| 性能度量 P | 天气信息准确、推荐符合天气和偏好、回答及时、预算合理 |
| 环境 E | 用户、天气服务、搜索引擎、景点信息、票务和交通情况 |
| 执行器 A | 调用天气 API、搜索 API、生成行程、向用户输出建议 |
| 传感器 S | 用户请求、天气 API 返回、搜索结果、用户后续反馈 |

分析一个 Agent 时，可以先问四个问题：

1. 怎样算完成得好？
2. 它处于什么环境？
3. 它能对环境做什么？
4. 它能从环境获得什么信息？

## 六、任务环境的几个重要特性

本章特别强调，真实环境往往不是简单、静态和完全可观察的。

- **部分可观察**：智能体只能看到 API 或传感器返回的部分信息。
- **随机性**：同一个行动不一定每次产生完全相同的结果，例如票价和库存会变化。
- **动态性**：智能体思考时，外部环境本身可能已经发生变化。
- **序贯性**：当前行动会影响后续状态，不能把每一步都当成独立任务。
- **多智能体性**：环境中可能存在其他用户、系统或智能体，它们也会改变环境。

这些特性解释了为什么 Agent 需要记忆、循环、重新规划和错误处理，而不是只执行一条固定指令。

## 七、反应式、规划式和混合式

从决策速度和规划深度看，可以分成三类：

- **反应式**：看到输入后快速行动，延迟低，但可能只顾眼前。
- **规划式**：行动前先分析多种未来方案，决策更有远见，但成本和延迟更高。
- **混合式**：底层快速响应，高层负责规划，是实际系统中更常见的形式。

LLM Agent 常见的“思考—行动—观察”循环，本质上是一种混合形式：

```text
Thought：进行规划和推理
Action：立即调用工具
Observation：获得环境反馈
```

## 八、神经符号主义的理解方式

本章用“系统 1 / 系统 2”帮助理解神经符号主义：

- **亚符号主义**：知识分布在神经网络中，擅长模式识别和自然语言理解，但解释性较弱。
- **符号主义**：知识以规则、逻辑和结构化形式表示，容易解释和验证，但面对开放环境较脆弱。
- **神经符号主义**：结合神经网络的感知能力和符号系统的结构化推理能力。

LLM Agent 可以看作一种实践形式：LLM 负责理解语言和生成计划，工具调用、参数、状态和执行结果则以较结构化的形式参与推理。

## 九、Workflow 和 Agent 的区别

最容易混淆的两个概念是 Workflow 和 Agent。

```text
Workflow：预先规定步骤，让系统按流程执行
Agent：给出目标，让系统自主决定步骤
```

| 对比项 | Workflow | Agent |
| --- | --- | --- |
| 流程 | 预先固定 | 动态生成或调整 |
| 决策 | 代码和条件分支决定 | LLM 根据上下文决定 |
| 可控性 | 高 | 相对较低 |
| 稳定性 | 高 | 依赖模型和工具质量 |
| 适合任务 | 规则明确、流程稳定 | 目标模糊、路径不确定 |
| 主要风险 | 难以覆盖例外情况 | 幻觉、循环、误调用工具 |

实际项目不一定非要二选一。更可靠的方案通常是：

```text
固定 Workflow 负责边界和关键审批
Agent 负责理解自然语言、拆解任务和处理开放部分
```

例如退款系统可以让 Workflow 负责金额、权限和最终审批，Agent 负责理解用户描述、提取信息和寻找政策条款。

## 十、旅行助手代码如何对应本章

当前的 `first_agent` 是本章 Agent Loop 的一个最小实现：

```text
用户请求
  ↓
LLM 生成 Thought / Action
  ↓
agent.py 解析 Action
  ↓
tools.py 执行天气或景点工具
  ↓
Observation 写回 prompt_history
  ↓
LLM 继续判断
  ↓
Finish[最终答案]
```

这个 demo 中最值得看懂的不是天气 API 或 Tavily 的具体用法，而是下面三层关系：

1. **提示词层**告诉模型有哪些工具、工具参数是什么、输出格式是什么。
2. **解析层**把模型生成的文本转换成真实的 Python 函数调用。
3. **循环层**把工具结果重新交给模型，使任务可以分步骤完成。

## 十二、复习检查点

合上文档后，可以先自己回答，再对照下面的参考答案。

### 1. 一个普通的 API 脚本和一个 Agent 的区别是什么？

普通 API 脚本通常按照开发者预先写好的固定顺序执行：输入参数、调用接口、处理结果，流程基本不会改变。

Agent 则以目标为导向，由模型根据当前观察结果决定下一步行动。它可以选择不同工具、调整执行顺序，并根据工具返回的结果继续规划。因此核心区别是：

```text
API 脚本：固定流程驱动执行
Agent：目标驱动决策，循环感知和行动
```

### 2. 为什么 LLM 本身不等于完整的 Agent？

LLM 主要负责理解文本、推理和生成内容，本身通常不能直接获取实时天气、修改数据库或执行外部操作。

完整的 Agent 还需要：

- 工具：让模型能够访问外部环境。
- 循环：让模型根据工具结果继续决策。
- 上下文或记忆：保存任务过程和观察结果。
- 执行控制：解析模型输出、执行工具并限制循环次数。

所以 LLM 更像 Agent 的决策核心，而 Agent 是由 LLM、工具、上下文和执行循环共同组成的系统。

### 3. `first_agent` 中谁负责感知，谁负责决策，谁负责行动？

- **感知**：`tools.py` 从天气 API 和 Tavily 搜索中获取环境信息；用户请求也是初始观察。
- **决策**：LLM 根据 `prompts.py` 中的系统提示词，生成 `Thought` 和 `Action`。
- **行动**：`agent.py` 解析 Action，并通过 `available_tools` 调用 `get_weather()` 或 `get_attraction()`。
- **反馈**：工具返回结果后，程序将其包装为 `Observation`，交给下一轮 LLM。

对应关系可以记为：

```text
tools.py 获取信息 → LLM 选择行动 → agent.py 执行工具 → Observation 返回
```

### 4. `prompt_history` 为什么是这个 demo 中不可缺少的部分？

因为 Agent 是多轮工作的。天气工具返回的结果必须被保存下来，下一轮模型才能知道天气是什么，并据此决定是否调用景点工具。

`run_agent()` 会把以下内容依次追加到 `prompt_history`：

```text
用户请求
模型输出的 Thought / Action
工具返回的 Observation
```

下一轮调用 LLM 时，程序通过 `"\n".join(prompt_history)` 把它们重新拼接成上下文。如果不保存 Observation，模型每一轮都会失去之前的工具结果，无法完成连续任务。

### 5. 如何用 PEAS 描述一个智能健身教练？

可以这样描述：

| PEAS | 智能健身教练内容 |
| --- | --- |
| 性能度量 P | 训练计划合理、动作纠正准确、达到用户目标、避免运动伤害 |
| 环境 E | 用户、健身房、运动设备、训练时间、用户当前身体状态 |
| 执行器 A | 语音指导、调整训练计划、提醒休息、给出饮食建议 |
| 传感器 S | 心率、运动强度、动作数据、用户反馈、训练历史 |

这个环境通常是部分可观察、动态、随机并且序贯的：智能体无法完全了解用户状态，用户的身体反应会变化，当前训练也会影响后续计划。

### 6. 天气查询场景为什么具有部分可观察、随机和动态特性？

- **部分可观察**：Agent 只能看到天气 API 返回的字段，不一定知道所有局部天气、道路情况或景点实时状态。
- **随机性**：天气预报和实际天气可能存在误差，多次查询结果也可能变化。
- **动态性**：天气、景点开放状态和票务信息会随着时间变化。
- **序贯性**：先查询天气，再根据天气选择景点，前一步结果会影响后续行动。

因此旅行助手不能只依赖一次固定判断，需要通过工具获取最新信息，并根据反馈动态调整。

### 7. 什么情况下固定 Workflow 比 Agent 更合适？

当任务规则明确、步骤稳定、结果要求可预测，或者涉及高风险审批时，固定 Workflow 更合适。例如：

- 固定格式的数据同步。
- 明确的报销审批流程。
- 金额和权限规则严格的退款处理。
- 必须保证每一步都可审计的金融、医疗流程。

Workflow 的优势是稳定、可控、容易测试和审计；如果任务不需要模型自主规划，就没有必要引入 Agent 的不确定性。

### 8. 为什么实际系统通常会把 Workflow 和 Agent 结合起来？

Workflow 擅长保证边界、顺序和关键规则，Agent 擅长理解自然语言、处理开放问题和动态选择工具。两者结合可以同时获得灵活性和可控性。

例如退款系统可以这样设计：

```text
Agent：理解用户描述、提取订单信息、查找相关政策
Workflow：校验金额、判断权限、执行审批和退款
```

让 Agent 负责不确定的理解任务，让 Workflow 负责不能出错的业务规则，通常比完全交给 Agent 更可靠。

### 9. 如果 Agent 没有 `max_steps`，可能出现什么问题？

Agent 可能因为以下原因一直循环：

- 模型不断生成无法执行的 Action。
- 工具持续返回错误，模型反复重试。
- 模型没有正确生成 `Finish`。
- 任务本身无法完成，但模型没有识别出来。

无限循环会导致 API 费用增加、程序无法结束，甚至持续修改外部环境。因此需要 `max_steps` 作为基本保护，同时还可以加入超时、重试次数、重复 Action 检测和人工介入。

### 10. 文本格式解析相比结构化工具调用有什么风险？

文本解析依赖模型严格遵守格式，例如：

```text
Action: get_weather(city="北京")
```

它的风险包括：

- 少写引号、换行不符合预期，就可能解析失败。
- 正则表达式难以处理嵌套对象、数组和复杂参数。
- 工具名和参数类型缺少可靠的 Schema 校验。
- 模型可能输出多余内容或多组 Action。
- 错误通常要等到运行时才发现。

原生 Function Calling 通常返回结构化的工具名称和参数，并支持参数 Schema 校验，因此稳定性更高。文本解析方案的优点是代码简单、适合入门，但不适合直接作为复杂生产系统的调用协议。

## 一句话总结

```text
Agent 不是一次模型回答，而是一个能够感知环境、调用工具、根据反馈继续决策，最终朝目标推进的闭环系统。
```
