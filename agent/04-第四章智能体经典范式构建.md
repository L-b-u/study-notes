# 第四章：智能体经典范式构建

参考资料：Datawhale `Hello-Agents` 第四章《智能体经典范式构建》。

本章第一次把前面学到的 LLM、Prompt、工具和记忆组合成真正可运行的 Agent。重点不是记住框架 API，而是理解三种不同的任务组织方式：

```text
ReAct：边思考，边行动，边观察
Plan-and-Solve：先生成完整计划，再按计划执行
Reflection：先执行，再反思，再优化
```

## 一、三种范式总览

| 范式 | 核心循环 | 最适合的问题 | 主要优势 | 主要代价 |
| --- | --- | --- | --- | --- |
| ReAct | Thought → Action → Observation | 需要实时信息和外部工具 | 灵活，能根据反馈动态调整 | 可能循环，输出解析较脆弱 |
| Plan-and-Solve | Plan → Step 1 → Step 2 → ... | 多步推理、步骤相对确定 | 结构清晰，执行过程稳定 | 计划出错后不一定能自动调整 |
| Reflection | Execute → Reflect → Refine | 代码、报告等需要质量迭代的任务 | 能发现问题并持续改进 | 调用次数多，延迟和成本高 |

## 二、公共基础组件

三种范式虽然循环方式不同，但都依赖几个公共组件：

### 1. LLM 客户端

负责封装模型调用，例如 `HelloAgentsLLM.think()`。主逻辑只需要传入消息，不必重复处理 API 地址、密钥和流式响应。

### 2. Prompt

Prompt 负责规定模型的角色、任务、上下文和输出格式。对于 Agent 来说，Prompt 不只是“让模型回答问题”，还要明确：

- 当前处于哪个阶段。
- 可以调用什么工具或使用什么信息。
- 输出必须采用什么结构。
- 什么时候终止。

### 3. 历史或记忆

Agent 需要把上一步的行动、结果或反馈保存下来，否则下一轮模型无法继续任务。

### 4. 循环控制

必须设置最大步数、最大迭代次数、超时或人工介入条件，防止模型反复调用、无限反思或持续消耗资源。

## 三、ReAct：Reasoning and Acting

### 1. 核心思想

ReAct 将推理和行动显式交替进行：

```text
Thought：分析问题，决定下一步
Action：调用工具或结束任务
Observation：读取工具返回结果
```

形式化地说，模型根据问题和历史轨迹生成当前思考与行动，工具执行行动后返回新的观察，再进入下一轮。

### 2. 为什么需要 ReAct

纯思考方法（例如 Chain-of-Thought）可以进行推理，但无法获得实时信息，容易产生幻觉；纯行动方法直接执行工具，又缺少规划和纠错。

ReAct 的优势在于：

```text
思考指导行动，行动结果又修正思考
```

### 3. 工具的三个要素

一个工具应包含：

| 要素 | 作用 |
| --- | --- |
| Name | 唯一名称，供模型在 Action 中调用 |
| Description | 描述什么时候使用工具，是模型选择工具的重要依据 |
| Execution Logic | 真正执行搜索、计算或 API 调用的函数 |

你在 `chapter4/React/tools.py` 中实现的 `search()` 和 `ToolExecutor` 就对应这一部分。

### 4. ReAct 代码结构

在你的项目中：

- `prompts.py`：定义 `Thought / Action / Finish` 输出协议。
- `tools.py`：实现 SerpApi 搜索和工具注册表。
- `agent.py`：解析模型输出，执行工具，保存 Observation。
- `main.py`：初始化 LLM、工具执行器和 Agent。

主循环可以记成：

```text
构造 Prompt
→ 调用 LLM
→ 解析 Thought / Action
→ Action 是 Finish：返回答案
→ 否则查找并执行工具
→ 写回 Action 和 Observation
→ 继续循环
```

### 5. ReAct 的风险

- 正则解析可能因为换行、括号、额外解释而失败。
- 模型可能选择不存在的工具或传入错误参数。
- 工具返回错误时，模型可能反复重试。
- 没有 `max_steps` 时可能无限循环。
- 工具结果未经验证时，错误信息可能继续传播。

## 四、Plan-and-Solve：先规划后执行

### 1. 核心思想

Plan-and-Solve 将任务拆成两个阶段：

```text
Planner：生成完整行动计划
Executor：严格按照计划逐步执行
```

它适合需要多个逻辑步骤、但执行路径相对确定的问题，例如水果销量计算、数学应用题和固定流程的数据分析。

### 2. Planner

规划器的 Prompt 要求模型输出结构化的 Python 列表：

```python
["计算周二销量", "计算周三销量", "计算三天总销量"]
```

代码使用 `ast.literal_eval()` 将列表文本安全转换成 Python 对象。相比直接解析自然语言，结构化输出更容易检查和执行。

你在 `chapter4/Plan_and_Solve/planner.py` 中完成了：

- 调用 LLM 生成计划。
- 提取 ```python 代码块。
- 使用 `ast.literal_eval` 解析。
- 检查结果是否为字符串列表。

### 3. Executor

执行器每次只处理计划中的当前步骤，并把结果写入历史：

```text
原始问题
完整计划
已经完成的步骤和结果
当前步骤
```

下一步会读取之前的历史，保证计算结果能够向后传递。

### 4. Plan-and-Solve 的优点和局限

优点：

- 任务结构清楚，便于观察和调试。
- 计划与执行职责分离。
- 对逻辑链条明确的任务更稳定。
- 可以单独检查计划是否合理。

局限：

- 一次性生成的计划可能从一开始就不正确。
- 执行过程中发现环境变化时，静态计划不一定适用。
- 计划步骤越多，上下文和调用成本越高。

改进方向是动态重规划：某一步失败或结果异常时，把失败原因和新状态交给 Planner，重新生成剩余计划，而不是盲目继续执行旧计划。

## 五、Reflection：执行、反思、优化

### 1. 核心思想

Reflection 不是第一次就要求模型给出完美答案，而是让模型经历质量迭代：

```text
初始执行 → 反思评审 → 根据反馈优化 → 再次反思 → 直到收敛
```

它尤其适合代码、技术报告、论文和复杂方案等“初稿可以先完成，之后再改进”的任务。

### 2. 三种角色 Prompt

- **Initial Prompt**：要求模型完成初稿，例如生成一个 Python 函数。
- **Reflect Prompt**：让模型扮演严格评审员，分析复杂度、漏洞和改进空间。
- **Refine Prompt**：把原始任务、上一版代码和反馈交给模型，要求生成新版本。

不同角色的 Prompt 很重要。执行者追求完成任务，评审者需要批判性，优化者需要落实反馈，不能简单地使用同一个提示词。

### 3. Memory 的作用

Reflection 必须记住每一轮的执行结果和评审意见。你在 `chapter4/Reflection/memory.py` 中使用 `records` 保存：

```python
{"type": "execution", "content": code}
{"type": "reflection", "content": feedback}
```

- `get_last_execution()`：获取最新代码，供下一轮评审。
- `get_trajectory()`：把完整执行—反思轨迹序列化成文本。

### 4. Reflection 的优点和代价

优点：

- 能发现初稿中的逻辑、性能和边界问题。
- 可以把“能运行”提升为“更高质量”。
- 适合复杂输出和高可靠性任务。

代价：

- 每轮至少增加反思和优化两次模型调用。
- 串行迭代导致延迟明显增加。
- 反思本身也可能错误，模型可能提出没有价值的修改。
- 如果没有清晰终止条件，可能过度优化或无限迭代。

## 六、三种范式如何选择

可以用下面的问题判断：

```text
需要实时查询或与外部环境交互吗？→ ReAct
任务是否可以先列出稳定步骤再执行？→ Plan-and-Solve
结果是否需要多轮质量提升？→ Reflection
```

更具体地说：

| 场景 | 推荐范式 |
| --- | --- |
| 查询新闻、天气、订单状态 | ReAct |
| 解决多步数学题 | Plan-and-Solve |
| 生成并优化代码 | Reflection |
| 预订机票、酒店、租车 | ReAct + Plan-and-Solve |
| 企业客服退款 | Workflow + ReAct + Reflection |
| 论文写作和审校 | Plan-and-Solve + Reflection |

实际项目通常不是三选一，而是组合使用：高层先规划，执行中调用工具，关键产出再反思验证。

## 九、复习检查点与答案

### 1. 三种范式在思考和行动组织方式上有什么区别？

ReAct 把思考和行动交替进行，每次行动后都读取环境反馈；Plan-and-Solve 先一次性生成计划，再按顺序执行步骤；Reflection 先生成结果，再让评审角色检查结果，根据反馈优化。

```text
ReAct：动态交替
Plan-and-Solve：先整体规划，再执行
Reflection：先完成，再迭代改进
```

### 2. 为什么 ReAct 适合搜索、天气和订单查询？

这些任务需要实时信息，模型本身的参数知识可能过时或不完整。ReAct 可以先思考需要什么信息，调用搜索或 API，再根据真实返回结果决定下一步，因此比一次性回答更可靠。

### 3. Plan-and-Solve 的静态计划执行失败时怎么办？

执行器应记录失败步骤、错误信息和当前环境状态，并把这些信息交给 Planner，要求重新规划剩余步骤。这样可以采用：

```text
执行步骤 → 检查结果 → 成功则继续
              ↓ 失败或异常
          更新状态并重新规划
```

不能简单地重复执行旧步骤，否则可能持续得到相同错误。

### 4. Reflection 为什么需要 Memory？

反思必须知道上一版输出是什么、之前指出了哪些问题以及已经尝试过哪些修改。Memory 保存执行结果和反馈，使下一轮优化有明确输入；没有 Memory，模型只能重新开始，无法形成真正的迭代。

### 5. Reflection 的“无需改进”终止条件是否足够？

它是一个简单可用的教学版本，但不够可靠，因为模型可能漏写这几个字，也可能错误地判断无需改进。更可靠的方式可以组合：最大迭代次数、代码测试是否通过、复杂度是否达到目标、反馈严重程度、连续两轮没有实质变化，以及人工审核。

### 6. 如何为电商客服设计混合范式？

可以采用：

- ReAct：查询订单、物流和退款记录。
- Workflow：严格执行金额、时间、权限和审批规则。
- Reflection：对争议较大的判断重新检查政策和证据。

Agent 负责理解自然语言和调用信息工具，确定性 Workflow 负责最终业务规则，高风险结果再交给 Reflection 或人工审核。

### 7. 为什么 ReAct 的工具描述很重要？

模型通常根据工具名称和自然语言描述判断什么时候调用工具。描述不清时，模型可能在该搜索时不用工具，或在不需要时错误调用。描述应说明工具用途、输入参数、返回结果和适用场景。

### 8. 正则解析 Action 有什么问题？如何改进？

模型可能增加解释、改变换行、使用嵌套参数或输出不完整括号，正则就可能解析失败。更稳妥的方式是使用原生 Function Calling、JSON Schema、Pydantic 校验或严格的结构化输出，并在解析失败时把错误反馈给模型重试。

### 9. 三种范式能否组合？

可以。例如预订商务旅行时，先用 Plan-and-Solve 生成机票、酒店和租车的高层计划；执行每一步时用 ReAct 查询实时库存和价格；最终方案生成后用 Reflection 检查预算、时间冲突和遗漏。

### 10. 为什么说 Reflection 是“以成本换质量”？

它通过额外的评审和优化调用提高结果质量，但每轮都会增加 Token 消耗、模型费用和等待时间。因此只有在代码、论文、技术报告等质量要求高且不要求瞬时响应的任务中，Reflection 的收益才值得这些成本。

## 一句话总结

```text
ReAct 解决“边做边看”，Plan-and-Solve 解决“先想清楚再做”，Reflection 解决“做完以后继续变好”。
```
